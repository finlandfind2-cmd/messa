# Миграция из монолита в набор микросервисов

Ниже — практичный план по выносу текущего PHP‑монолита в микросервисную архитектуру с сохранением функционала и оптимизацией под VPS (ограниченные CPU/RAM/диск).

## 1. Декомпозиция по доменам
Рекомендуемые сервисы и их границы исходя из текущих модулей (`src/Services`, `src/Controllers`, `src/Domain`):
- **API Gateway** — единственная публичная точка входа (HTTP). Terminate TLS, rate‑limit, маршрутит на бэкенды, добавляет кэширование для публичных файлов/аватаров. Можно начать с Nginx + Lua/OpenResty или легковесного Fastify/Node.
- **Auth Service** — регистрация/логин/OTP/JWT/сессии (`AuthAggregateService`, `OtpService`, `JwtService`, `SessionService`). Хранит пользователей и сессии, отдаёт короткоживущие токены.
- **Chat Service** — работа с чатами/сообщениями (`Domain/Messages`, контроллеры `Chats`, `Messages`). Содержит бизнес‑логику отправки/чтения, long‑poll/updates.
- **Media Service** — загрузка/хранение медиа/аватаров (`Services/Media`, `AvatarService`, `Telemost`, `S3`). Инкапсулирует S3/локальное хранилище и фоновые задачи ffmpeg.
- **Notification Service** — отправка событий/вебхуков/ботов (`TelegramBot`, e‑mail/SMS), очередь задач.
- **Settings/Profile Service** — пользовательские настройки (`SettingsService`). При небольшом объёме можно оставить внутри Auth.
- **Health/Monitoring** — лёгкий сервис, агрегирующий проверки зависимостей (DB/Redis/S3) с конфигом по env.

## 2. Контракты и API
- Описать REST/gRPC контракты между сервисами (OpenAPI для Gateway ↔️ сервисы, protobuf/JSON для внутренних вызовов).
- Общие DTO вынести в отдельный пакет (composer package или git submodule) с versioning.
- Внешние клиенты ходят только через Gateway; прямые вызовы между сервисами ограничить приватной сетью.

## 3. Хранение данных
- **Базы**: разделить схемы по сервисам (Auth DB, Chat DB, Media DB). Общие таблицы (пользователи) доступны через API, а не прямыми JOIN.
- **Миграции**: сначала читать из монолитной базы, затем реплицировать в новые схемы, позже переключить запись.
- **Кэш**: Redis по возможности общий, но с namespace на сервис; предусмотреть in‑memory фоллбек для VPS.

## 4. Асинхронные операции
- Ввести брокер (Redis Streams/RabbitMQ/SMTP) для очередей медиаконвертации, уведомлений, вебхуков.
- Обернуть long‑poll `/v1/updates` в push‑модель: WebSocket/SSE через Gateway с бекенд‑воркером (Chat Service) либо брокер событий.
- Медиа‑воркеры проверяют наличие ffmpeg и деградируют до копирования без перекодирования.

## 5. Сетевые паттерны и устойчивость
- Circuit breaker/timeout/retry для внутренних RPC с экспоненциальной паузой.
- Centralized tracing (OpenTelemetry) с минимальной выборкой, логгирование в stdout (готово для systemd/journal на VPS).
- Health‑checks лёгкие и конфигурируемые: отдельно liveness (без зависимостей) и readiness (с проверкой нужных сервисов по env).

## 6. Оптимизация под VPS
- Память: ограничить PHP‑FPM воркеры, включить OPcache, использовать `swoole`/RoadRunner только если есть ресурсы.
- CPU: включить HTTP‑кэш для статичных аватаров/фронта, кэшировать ответы справочников на Gateway.
- Диск: локальный storage для временных файлов, периодическая очистка, опциональное S3.
- Безопасность: минимальный набор расширений, отключить `display_errors`, лог в stdout, никакого произвольного `debug.log`.

## 7. Пошаговая миграция (инкрементально, без даунтайма)
1. **Подготовка**: добавить feature‑флаги на использование Auth/Media/Chat сервисов из монолита; сделать конфиг health‑check.
2. **Gateway**: вынести публичные маршруты в Nginx/OpenResty, пробросить в монолит как backend #1.
3. **Auth Service v1**: выделить авторизацию и выдачу токенов в отдельный контейнер/VM. Монолит начинает ходить к нему через HTTP client.
4. **Media Service v1**: вынести загрузку/выдачу файлов + очередь конвертации. Перевести аватары на CDN/статический Gateway cache.
5. **Chat Service v1**: вынести CRUD чатов/сообщений, заменить прямые вызовы БД на RPC. В этот момент long‑poll мигрирует на SSE/WebSocket слой.
6. **Notifications**: вынести ботов/вебхуки, подписать Chat/Auth события на очередь.
7. **Декомиссия монолита**: удалить мёртвый код, оставить слой совместимости в Gateway.

## 8. CI/CD и релизы
- Отдельные Docker‑образы для каждого сервиса с health‑check и минимальными зависимостями.
- Общие шаги линтинга/тестов вынести в reusable GitHub Actions; нагрузочные тесты для Chat/Media.
- Blue/Green или Canary деплой через `docker-compose`/`nomad`/`k8s` (минимальный кластер) или systemd‑юниты на VPS.

## 9. Monitoring & SLO
- Бюджет доступности: Auth/Chat — p99 latency < 200–300ms на VPS, Media — асинхронно с очередью.
- Метрики: RPS, latency, error rate, queue depth, ffmpeg duration, кэш hit‑ratio.
- Алёрты: деградация кэша, рост 5xx на Gateway, переполнение диска/очереди.

## 10. Быстрые выигрыши (что можно сделать сразу)
- Включить env‑конфиг для логов/health‑check/Redis/S3.
- Добавить HTTP Gateway с кэшем для статики и rate‑limit.
- Ввести брокер задач и вынести медиаконвертацию в отдельный процесс.
- Перевести long‑poll на SSE/WebSocket через отдельный воркер, чтобы не держать PHP‑FPM воркеры.

Этот план позволяет поэтапно разрезать монолит, сохранить существующие функции и сделать сервисы устойчивыми и экономичными на VPS.
