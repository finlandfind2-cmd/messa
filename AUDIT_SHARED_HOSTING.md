# Дополнительные проблемы для shared-хостинга

10) **/public/health.php падает без Redis и не отдаёт health.** Файл создаёт `CacheService` до любой проверки; его конструктор сразу открывает соединение с Redis, и при недоступности сервиса health-check завершится исключением ещё до JSON-ответа. На shared-хостингах Redis часто отсутствует, поэтому health должен работать с in-memory кэшем или просто без него. 

:::task-stub{title="Сделать health.php нечувствительным к отсутствию Redis"}
- В `public/health.php` обернуть создание `CacheService` в try/catch, при ошибке использовать локальный расчёт без Redis или простой статический кеш в памяти.
- Добавить флаг окружения `HEALTH_USE_CACHE` для явного отключения внешнего кеширования.
- Возвращать health даже при деградации кэша, логируя проблему вместо фатала.
:::

11) **Bootstrap CLI всегда пингует Redis.** `Bootstrap::initCli()` делает `Redis::client()->ping()` на каждом запуске воркера/cron-задачи; при закрытом порте Redis это добавляет задержку или фатал ещё до выполнения полезной работы. Для shared-хостинга нужен флаг отключения или мягкое ветвление без обращения к Redis. 

:::task-stub{title="Убрать обязательный Redis-ping из initCli"}
- В `src/Core/Bootstrap.php` читать env-переключатель (например, `REDIS_OPTIONAL`) и пропускать ping при выключенном Redis.
- При ошибке соединения сразу помечать Redis как недоступный в логах, но не останавливать процесс.
- Покрыть запуск CLI-инициализации тестом/фикстурой без поднятого Redis.
:::

12) **Публичный /v1/health раскрывает конфиденциальные метрики и делает тяжёлые COUNT-запросы.** Контроллер без авторизации отдаёт версии БД, размер памяти Redis и при `full=1` выполняет `COUNT(*)` по крупным таблицам, что на shared-хостинге легко уронит БД и раскрывает внутренние данные. Нужно выключаемый расширенный режим и маскирование подробностей.

:::task-stub{title="Сделать health-метрики лёгкими и непубличными"}
- В `HealthController` убрать/зафичерфлагить выдачу db_version/redis_info и COUNT(*) по таблицам; по умолчанию отдавать только простые пинги.
- Добавить auth-требование или секретный ключ для `full=1`, либо отключить параметр на проде через env.
- Ограничить время выполнения health-запросов (таймауты/try-catch) и документировать безопасный режим для shared-хостинга.
:::

13) **S3-клиент падает ещё до health-check при пустых переменных окружения.** В `S3::client()` аргумент `S3_ENDPOINT` берётся без дефолта и сразу прокидывается в `rtrim()`, что вызовет TypeError, если переменная не задана; аналогично `S3_KEY/S3_SECRET` могут быть пустыми, но клиент создаётся всё равно. На shared-хостинге без S3 такой вызов завершит скрипт до graceful-фоллбека, включая health и загрузки медиа.

:::task-stub{title="Защитить S3::client от пустой конфигурации"}
- В `src/Core/S3.php` проверять все требуемые env (`S3_ENDPOINT`, `S3_BUCKET`, ключ/секрет) до вызова S3Client и выходить с контролируемым исключением/false.
- Оборачивать создание клиента в try/catch и разрешать отключение S3 через `S3_ENABLED=0`, чтобы health/медиа могли работать в деградированном режиме.
- Добавить юнит для `S3::client()`/`isAlive()` при пустых env, подтверждающий отсутствие TypeError и корректный фоллбэк.
:::

14) **AvatarService всегда поднимает S3Client и требует полный доступ к бакету.** Конструктор создаёт S3Client без таймаутов/исключений и с пустыми значениями по умолчанию; при отсутствии расширения curl/OpenSSL или переменных S3 это приведёт к фаталу даже если аватары не используются. На shared-хостинге это критично, потому что доступ к S3 часто выключен.

:::task-stub{title="Ленивый и отключаемый AvatarService"}
- Инициализировать S3Client в `AvatarService` лениво в методе `presignUserAvatarPut`, проверяя флаг `S3_ENABLED` и наличие конфигурации.
- Проставить безопасные таймауты и обработку ошибок создания клиента; при недоступности S3 отдавать явный ответ/код ошибки без падения процесса.
- Документировать поведение сервиса аватаров при отключённом S3 и добавить тесты на отсутствие фаталов без env.
:::

15) **Долгое блокирующее long-polling держит PHP-FPM воркеры по 20 секунд.** `/v1/updates` использует `XREAD ... BLOCK` до 20 000 мс и семафор в Redis; на shared-хостинге с малым числом воркеров это вычерпывает пул, а при недоступности Redis endpoint сразу отдаёт 503. Нужна опция отключения long-poll или переход на короткие опросы/SSE.

:::task-stub{title="Сделать updates.poll неблокирующим для shared"}
- Добавить env-переключатель (например, `UPDATES_ENABLE_LONGPOLL`) и при выключении всегда отвечать 204 без блокировки или с коротким таймаутом.
- При недоступном Redis не отдавать 503, а возвращать пустой ответ с заголовком `Retry-After`, чтобы фронт мог деградировать.
- Рассмотреть ограничение `block_ms` до 1–2 с и тесты, что обработчик не держит воркер дольше заданного лимита.
:::
